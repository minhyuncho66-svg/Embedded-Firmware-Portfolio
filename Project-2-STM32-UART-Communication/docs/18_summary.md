18_인터럽트 수신 / 링버퍼

학습 내용
- 인터럽트 사용 이유
  - 폴링방식의 문제점: 폴링방식으로 신호를 확인하면 while(1) 안에서 반복하며 데이터가 왔는지 확인하는데 
    정작 오는 건 한 번임에도 여러 번 확인하게 되어 낭비가 발생할 수 있으며 1초동안 코드가 멈추는 
    상황(HAL_Delay 등)이라면 상대가 보내도 확인할 기회조차 놓쳐버릴 수 있음
    따라서 CPU가 무엇을 하던 간에 하드웨어(UART 수신회로)가 데이터를 받으면 자동으로 CPU에게 "지금 하던 일을 
    멈추고 이것부터 처리하라"고 알려주는 인터럽트 방식을 사용하면 폴링의 문제점을 해결할 수 있음

- 인터럽트 사용 방식
  - 콜백함수(HAL_UART_RxCpltCallback)에 하드웨어가 데이터를 받을 때 실행할 코드를 미리 작성해둠
  - 링버퍼 사용: 콜백함수는 1바이트씩 도착할 때마다 실행되므로 순환버퍼인 링버퍼에 받은 글자들을 쌓아두고 
    while(1) 메인 루프에서 꺼내어 조립해 사용
  - push/pop 함수: 링버퍼 내부에 push로 데이터를 넣고 pop으로 넣은 데이터를 꺼내서 반환

학습 중 생긴 의문 1
- head가 배열 크기(256)를 넘어갈 때 어떻게 다시 처음으로 돌아가게 만들 수 있을지 헷갈렸음

답변 1
- % 연산자(나머지 연산)를 이용해 head = (head+1) % 256으로 구현. head가 255일 때 +1하면 256이 되는데 
  256 % 256 = 0이 되어 자동으로 처음 위치로 돌아가는 원형 구조가 만들어짐

학습 중 생긴 의문 2
- 콜백 함수(HAL_UART_RxCpltCallback)의 구조를 처음엔 검색해서 그대로 가져다 썼는데, 왜 이런 이름과 구조여야 
  하는지 완전히 이해하지 못한 채 사용하고 있다는 걸 스스로 인지함

답변 2
- 함수 이름이 정확히 일치해야 하는 이유: 이 함수는 우리가 직접 호출하는 게 아니라 하드웨어가 자동으로 호출하는   
  것이라 HAL 라이브러리 내부에 미리 정해진 이름을 그대로 다시 정의(재정의)해야만 인식됨
- if(huart->Instance == USART2) 조건이 필요한 이유: STM32에는 USART1, 2, 3 등 여러 채널이 있을 수 있어 
  지금 인터럽트가 어느 채널에서 발생했는지 구분해야 함
- HAL_UART_Receive_IT()를 콜백 안에서 재호출하는 이유: 이 함수는 "1바이트 받을 준비"를 딱 1번만 해주기 때문에
  다음 바이트도 받으려면 매번 콜백 안에서 다시 호출해줘야 함

학습 중 생긴 의문 3
- 코드는 0 errors로 정상 빌드되고 TX(Hello STM32 송신)는 잘 되는데 RX(Echo)만 전혀 작동하지 않는 문제 발생

답변 3
- 디버깅 과정:
  1) 먼저 TX만 별도로 테스트해서 UART 연결 자체는 정상임을 확인
  2) HAL_UART_RxCpltCallback 함수 첫 줄에 브레이크포인트를 
     걸고 디버그 모드로 실행 → 문자를 입력해도 전혀 멈추지 않음을 확인 → 콜백 함수 자체가 호출되지 않고 
     있다는 것을 파악
  3) stm32f4xx_it.c 파일에 USART2_IRQHandler 함수가 아예 없다는 것을 발견 → 인터럽트가 발생해도 
     콜백 함수로 연결해줄 통로 자체가 없었던 것이 원인
  4) CubeMX(.ioc)에서 USART2의 NVIC Settings에 있는 USART2 global interrupt가 체크되지 않은 것을 발견 
     체크 후 Generate Code를 다시 실행하여 해결

  - 배운 것: CubeMX에서 설정만 바꾸고 Generate Code를 다시 누르지 않으면 실제 코드에 반영되지 않는다는 것 
  그리고 코드 문법이 아니라 설정이 코드에 반영되지 않은종류의 버그도 있다는 것을 체감함

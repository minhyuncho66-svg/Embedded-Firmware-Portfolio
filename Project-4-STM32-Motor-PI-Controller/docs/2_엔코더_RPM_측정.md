1. 목표
타이머 Encoder Mode로 실시간 RPM 측정
2. 학습 내용

&#x20; -ppr(pulses per revolution) 개념, 감속비(1:50) 반영해서 실제 펄스수(350) 계산
   -> ppr이란 모터축이 바뀔때마다 나오는 펄스의 개수를 의미하며 감속비(1:50)은 내부의 존재하는
       모터가 50바퀴를 돌아야 기어를 거친 최종 출력이 1바퀴를 도는것을 의미한다 이에 따라 현재
       사용중인 N20모터는 7ppr값을 가지고 최종 출력축의 1바퀴에 350펄스의 신호를 출력한다.

&#x20; -엔코더 채널 A/B 2개가 필요한 이유 (위상차로 회전방향 판별)
   -> 엔코더는 모터 내부 축에 붙어있는 센서 A/B가 위치상 미세하게 어긋나 있어 축이 회전할 때
       두 센서의 신호가 시간차를 두고 발생한다. A가 먼저 반응하는지 B가 먼저 반응하는지(신호 순서)로
       회전 방향을 판별하는 구조. 이를 위해 두 채널을 동시에 감지하는 CubeMX Encoder Mode
(TI1 and TI2) 설정 필요"

\-카운터 오버플로우 안전성 직접 계산 검증 (최대속도 가정 → 0.1초당 펄스수 → 65535와 비교)
->일반적인 모터의 최대속도를 300RPM으로 가정했을시 1분에 300바퀴를 돌며 1초에는 5바퀴,
0.1초에는  0.5바퀴 즉 0.1초를 RPM의 측정시간이라 계산했을시 모터는 총 175펄스(0.5x350)를
출력하며 설정한 카운터 최대값인 65535안에서 구현 가능할것이라 검증

\-\_\_HAL\_TIM\_GET\_COUNTER, \_\_HAL\_TIM\_SET\_COUNTER로 펄스 카운트 읽기/리셋
->먼저 모터를 동작시키고 그에 따른 rpm값을 UART로 송신하고 PUTTY로 출력되는 값 확인

\-측정주기(Delay)와 환산배율(×N)이 항상 짝을 이뤄 함께 바뀌어야 하는 원리
-> 카운터값을 계산시 몇초마다 읽을지에 대한 값을 환산배율로 계산함에 따라 이 환산배율이 변할시
측정주기 또한 함께 바뀌어야한다.

3. 시행착오
-정수 나눗셈 함정 ((count\*10)/350이 0으로 나올 뻔했던 경우)
-> 환산배율로 계산하는 과정에서 int16\_t로 선언한 정수형 카운터 변수를 1초당 바퀴수를 계산하기
위해 350으로 나눌시 정수형 / 정수형 일때는 몫이 아에 안나오는 경우도 존재하기에 이를 아에
실수형으로 선언하고 나누는쪽을 .0f로 수정하여 몫이 나올 수 있게 변경
4. 배운 것
서로 다른 목적(모터 방향전환 테스트 vs 실시간 RPM 측정)을 하나의 루프에 섞으면 측정값이
왜곡된다는 것 → 목적별로 루프 구조를 분리해야 한다는 설계 원칙
